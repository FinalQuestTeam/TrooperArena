console.h Console de texto TTY

Este módulo fornece um console de texto simples no estilo TTY. Os caracteres são escritos como um fluxo contínuo: as linhas quebram automaticamente quando a borda horizontal da tela é atingida e, ao chegar à parte inferior da janela, o conteúdo do console rola uma linha para cima e uma linha em branco é inserida. Por padrão, o console ocupa uma tela padrão de 40x28 tiles, e todos os atributos de texto (fonte, paleta, plano etc.) são herdados das configurações de texto do SGDK. As atualizações de tela são feitas por DMA (método alterável com CON_setTransferMethod()). Um dos principais casos de uso são mensagens de assert: o estado do Genesis pode ser resetado automaticamente antes da exibição do texto (veja a macro con_assert). O módulo só é compilado quando MODULE_CONSOLE != 0 em config.h.

con_assert(condition)

Macro funcional que verifica uma condição (assert). Se a expressão avaliar como falsa, o console é resetado (CON_reset()), o sistema é agendado para reset no próximo write (CON_systemResetOnNextWrite()), uma mensagem de erro com arquivo, linha e a condição que falhou é impressa no console e a execução trava em um laço infinito.

Pode ser desabilitada definindo NDEBUG ou usando o build de release do SGDK (LIB_DEBUG=0) — nesses casos a macro expande para nada.

Define o tamanho do buffer de caracteres usado internamente para compor a string formatada impressa no console. Ao chamar esta função, a memória do buffer anterior é liberada imediatamente; o novo buffer é alocado na próxima chamada a CON_write(). O padrão é 160 caracteres.

void CON_setTransferMethod(TransferMethod tm)

Define o método de transferência usado para enviar o tile buffer do console à VRAM do VDP (usado com VDP_setTileMapDataRect()). O valor padrão é DMA, que faz upload imediato.

Reseta o console às configurações padrão. É um atalho para: CON_setConsoleSize(0, 0, 40, 28), CON_setLineBufferSize(160) e CON_setTransferMethod(DMA).

everdrive.h Suporte ao flashcart Everdrive

Este módulo, escrito por Krikzz (criador do hardware), fornece suporte ao flashcart Everdrive para Mega Drive. Ele expõe os registradores de hardware do cartucho (porta SPI, configuração, mapeamento de ROM etc.), macros de controle e funções de baixo nível para acessar o cartão SD/MMC do cartucho e a memória flash (EPROM) interna. Use-o apenas quando o jogo/aplicação for executado em um cartucho Everdrive real — é a base sobre a qual o módulo fat16.h funciona. Compilado somente quando MODULE_EVERDRIVE != 0. A variável global extern u16 cfg mantém a cópia em RAM do registrador de configuração.

fat16.h Sistema de arquivos FAT16 (Everdrive)

Este módulo, também de autoria de Krikzz, fornece suporte básico ao sistema de arquivos FAT16 através do hardware do flashcart Everdrive (usa as rotinas de SD/MMC de everdrive.h por baixo). Permite inicializar a partição, listar diretórios, abrir, ler, escrever, criar e apagar arquivos no cartão SD do Everdrive. Use-o somente em conjunto com um cartucho Everdrive; requer MODULE_FAT16 != 0 (e, na prática, o módulo Everdrive habilitado). A variável global extern Fat16PBR fat16_pbr guarda o Partition Boot Record lido na inicialização. link_cable.h Protocolo de comunicação via Link Cable (LCP)

O Link Cable Protocol (LCP), de autoria de BlodTor (2025), é um protocolo de troca de dados via SEGA Link Cable entre dois consoles Mega Drive / Genesis conectados pela porta do segundo controle (porta 2). Um console atua como master e o outro como slave: o master chama LCP_masterCycle() no código principal do jogo para disparar uma interrupção externa (EX-INT, nível 2 do 68000) no slave, cujo tratador troca os pacotes de forma assíncrona. Os dados são serializados em pacotes de objetos tipados — 2 bytes de tipo seguidos dos dados do objeto (transferidos 2 bytes por ciclo) — com verificação por checksum. Use este módulo para jogos multiplayer em dois consoles. Compilado quando MODULE_LINK_CABLE != 0.

Sequência típica no master: LCP_init() → LCP_objectToPacketForSend() (uma ou mais vezes) → LCP_masterCycle() → LCP_getNextObjectFromReceivePacket() até retornar 0 → LCP_close(). No slave: LCP_init() → LCP_open() → LCP_objectToPacketForSend() → (troca ocorre no tratador de interrupção) → LCP_getNextObjectFromReceivePacket() até 0 → LCP_close(). Importante: os tipos de objeto (objectType), a tabela de tamanhos (objectSizes, em bytes, múltiplos de 2) e a lógica que decide qual console é master/slave devem ser definidos no código do SEU jogo (veja os exemplos do jogo 'Super Turbo MEGA Pac-Man 2.1'). Para depurar erros de transmissão, use LCP_getError().

Funções

void LCP_open()

Abre a porta 2 do console para troca de dados via Link Cable por interrupção externa EX-INT (máscara de interrupção nível 2 do Motorola 68000) e configura a função de callback chamada quando a interrupção ocorre. Deve ser chamada no console slave: só depois dela o master consegue acionar o tratador LCP_slaveCycle() no slave.

void LCP_init()

Inicializa a porta 2 do console para troca de dados via Link Cable, no modo de escrita direta na porta e posterior leitura. As interrupções EX-INT ficam desabilitadas para este console e as variáveis globais do protocolo são zeradas. Primeira função a chamar tanto no master quanto no slave.

void LCP_close()

Fecha a porta do console para a troca de dados via Link Cable, desabilitando o tratador de interrupção externa EX-INT (nível 2 do 68000). Após o fechamento no slave, ele deixa de responder às interrupções externas geradas pelo master.

void LCP_objectToPacketForSend(u8 *transferObject, u16 objectType, u16 *objectTypeSizes)

Copia o objeto transferObject, como array de bytes, para o pacote de envio (LCP_sendPacket) a ser transmitido via Link Cable. Estrutura do pacote: os 2 primeiros bytes contêm o tipo do objeto (nunca 0), seguidos dos dados do objeto (de 2 em 2 bytes) conforme a tabela objectTypeSizes. Vários objetos podem ser enfileirados em sequência, enquanto couberem no buffer.

ParâmetroDescrição
transferObjectObjeto a enviar, tratado como array de bytes.
objectTypeTipo do objeto (número que corresponde ao índice no array de tamanhos). Não pode ser 0.
objectTypeSizesArray com os tamanhos de cada tipo de objeto (definido no código principal do SEU jogo).

Códigos de erro (obtidos por LCP_getError() & 0x000F): 0xC — tamanho do objeto negativo ou zero; 0xD — tamanho do objeto excede o espaço restante do pacote; 0xF — índice de início dos dados do pacote maior que o índice de fim.

u16 LCP_getNextObjectFromReceivePacket(u8 *transferObject, u16 *objectSizes)

Extrai o próximo objeto, como array de bytes, do pacote recebido (LCP_ReceivePacket) via Link Cable. Como vários objetos podem ser transmitidos de uma vez, chame esta função repetidamente até que retorne 0, indicando que todos os objetos foram extraídos.

ParâmetroDescrição
transferObjectBuffer que recebe o próximo objeto extraído do pacote.
objectSizesArray com os tamanhos de cada tipo de objeto (definido no código principal do SEU jogo).

Retorna: o tipo do objeto recebido, ou 0 se nenhum objeto pôde ser extraído do pacote.

Códigos de erro (LCP_getError() & 0xF000): 0x1000 — não há objeto no pacote (todos já extraídos ou nada transmitido); 0x2000 — tamanho do objeto a extrair negativo ou zero; 0x3000 — tamanho excede os dados restantes do pacote recebido; 0x4000 — tamanho excede o espaço restante do array LCP_ReceivePacket.

void LCP_masterCycle()

Ciclo de transmissão e recepção de dados via Link Cable para o console master. No início, desabilita todo o processamento de interrupções e zera LCP_timeOut e LCP_error. Dispara a interrupção externa no slave, envia o pacote de saída (tamanho, dados, checksum) e recebe o pacote de resposta do slave, validando checksums. Tanto em caso de erro quanto de sucesso, ao final chama internamente LCP_masterCycleEnd() para restaurar o estado correto da porta 2 e reabilitar as interrupções.

Códigos de erro (LCP_getError() & 0x00F0): 0x10 — falha em LCP_startSendCycle() (início da transmissão); 0x20 — falha no envio do tamanho do pacote; 0x30 — falha no envio dos dados do pacote; 0x40 — falha no envio do checksum; 0x50 — falha em LCP_endSendCycle(); 0x60 — falha em LCP_startReceiveCycle(); 0x70 — falha na recepção do checksum do slave; 0x80 — checksum calculado difere do recebido; 0x90 — falha na recepção do tamanho do pacote; 0xA0 — falha na recepção dos dados; 0xB0 — falha no ciclo principal de recepção do checksum; 0xC0 — checksum calculado difere do recebido; 0xD0 — falha em LCP_endReceiveCycle(); 0xE0 — falha ao iniciar o envio do checksum ao slave; 0xF0 — falha no envio do checksum ao slave.

u16 LCP_getError()

Retorna o registro de erros da transmissão de dados via SEGA Link Cable. Se o valor for 0x0000, nenhum erro ocorreu. O código é dividido em nibbles: os 4 bits baixos do byte baixo (0x0001–0x000F) indicam erros de recepção de dados; os 4 bits altos do byte baixo (0x0010–0x00F0), erros de transmissão; os 4 bits baixos do byte alto (0x0100–0x0F00), erros de recepção/transmissão de pacote; e os 4 bits altos do byte alto (0x1000–0xF000), erros de extração de objetos do pacote.

Retorna: o valor de LCP_error.

flash.h Interface de baixo nível para flash NOR

Módulo de Jesus Alonso (doragasu) para leitura, apagamento e escrita de dados diretamente no chip flash NOR do cartucho. Funciona com qualquer chip compatível com o formato AMD que implemente a interface CFI (testado com S29GL032 e W29GL032C), e exige que o cartucho tenha a linha #WE conectada ao chip (caso da maioria dos flashcarts, mas não garantido). É a base do sistema de save em flash para cartuchos sem SRAM/EEPROM — normalmente usado através do módulo de mais alto nível saveman.h.

Limitações importantes: endereços devem ser pares, ponteiros de dados devem estar alinhados a word, e as funções flash_init(), flash_sector_erase() e flash_program() (além de flash_copy()) devem ser executadas com interrupções desabilitadas e o Z80 parado. A flash sofre desgaste (wear): evite salvar com muita frequência ou implemente wear leveling. Recomenda-se fortemente que o cartucho tenha o pino #RESET ligado ao sinal #RESET do console; caso contrário, um RESET durante apagamento/gravação provavelmente congelará a máquina.

saveman.h Gerenciador de saves em flash

Gerenciador de saves (save manager) de Jesus Alonso (doragasu) para chips flash suportados pelo módulo flash.h. Permite salvar dados não voláteis na própria flash do cartucho — a solução ideal para cartuchos sem SRAM/EEPROM. Suporta quantos slots de save forem necessários, cada um com comprimento arbitrário de dados (ex.: slot 0 para configuração do jogo, slot 1 para recordes e slots 2 a 4 para partidas salvas). Cada gravação em um slot substitui o conteúdo anterior. O módulo usa dois setores da flash para implementar wear leveling e gravação segura: o save não é perdido mesmo se houver corte de energia durante a operação.

Os flashcarts típicos (como o Flash Kit Cart do Krikzz) usam setores de 64 KiB no fim da flash, então por padrão o módulo ocupa os 128 KiB superiores do espaço de ROM — se código/dados do jogo caírem nessa área, serão apagados! Há como usar setores de 8 KiB (gastando 16 KiB em vez de 128 KiB), mas é mais delicado; o layout padrão reduz o desgaste e permite saves maiores. Todos os slots (mais os cabeçalhos internos) devem caber em um único setor. Os dois setores usados são os indicados pela faixa de memória declarada no cabeçalho da ROM no offset 0x1B4. Uso típico: sm_init() → sm_load() / sm_save() / sm_delete() → sm_clear() para reset de fábrica. Exceto sm_load(), todas as funções param o Z80 e desabilitam interrupções até retornarem — garanta que não há música/som tocando ao chamá-las. Buffers de save/load devem estar alinhados a word (use __attribute__((aligned(2))) em arrays de char), senão ocorre SM_STAT_INVALID_PARAM_ERR.

Tipos

enum (códigos de status SM_STAT_*)

Enum anônimo com os códigos de status retornados pelas funções do módulo.

enum {
    SM_STAT_PARAM_ERR    = -3, // parâmetro inválido na chamada
    SM_STAT_HW_ERR       = -2, // erro de hardware do chip flash
    SM_STAT_ERR          = -1, // erro genérico
    SM_STAT_OK           =  0, // sucesso
    SM_STAT_WARN_NO_DATA =  1, // sucesso, mas o chip não tem dados salvos
};

Funções

int16_t sm_init(uint8_t num_slots)

Inicializa o módulo gerenciador de saves. Deve ser chamada uma vez, antes de qualquer outra função do módulo, e sempre com os mesmos parâmetros. Chama flash_init() internamente — não a chame por conta própria.

ParâmetroDescrição
num_slotsNúmero de slots de save a suportar.

Retorna: SM_STAT_OK se a inicialização teve sucesso e há dados para carregar; SM_STAT_WARN_NO_DATA se teve sucesso mas não há dados salvos; SM_STAT_PARAM_ERR se os parâmetros são inválidos; SM_STAT_HW_ERR se o chip flash falhou em alguma operação; SM_STAT_ERR (SM_ERR) para outro erro irrecuperável.

Para o Z80 e desabilita interrupções até terminar. Usa os dois setores adjacentes na faixa de memória especificada no cabeçalho da ROM no offset 0x1B4; se a faixa não casar exatamente com dois setores adjacentes da flash, retorna SM_STAT_PARAM_ERR. ATENÇÃO: os dois setores usados não podem conter código — não faça seu jogo apagar a si mesmo!

Para o Z80 e desabilita interrupções até terminar. Se alguma gravação retornar SM_STAT_HW_ERR, algo estranho aconteceu: o melhor é reiniciar o console, ou ao menos desinicializar e reinicializar o módulo para que a rotina de init tente corrigir o problema e evitar mais perda de dados.

minimus.h Driver de som MiniMusic

Interface do driver de som MiniMusic para o Z80: um driver alternativo e minimalista aos drivers de som padrão do SGDK. O programa do driver (blob binário) é carregado na RAM do Z80 com minimusic_init(), e a comunicação com o 68000 é feita por comandos de 1 byte (minimusic_sendcmd()) e leitura de status (minimusic_get_status()). O header também fornece macros/funções inline de sincronização com o Z80 via bus request (endereço 0xA11100), usadas para acessar com segurança a memória compartilhada. Use este módulo quando quiser tocar música/efeitos com o driver MiniMusic em vez dos drivers nativos do SGDK.

MINIMUSIC_MEMORY_BARRIER()

Macro funcional que insere uma barreira de memória do compilador (asm volatile ("" : : : "memory")), impedindo que o compilador reordene acessos à memória ao redor dela. Usada internamente pelas funções de guarda do Z80.

Inicia uma seção crítica de acesso ao barramento do Z80: escreve 0x100 no registrador de bus request (0xA11100), solicitando o barramento e pausando o Z80, com barreiras de memória antes e depois. Chame antes de acessar a RAM do Z80 diretamente.

static inline void MINIMUSIC_Z80_GUARD_END()

Encerra a seção crítica: escreve 0x000 no registrador de bus request (0xA11100), devolvendo o barramento e retomando a execução do Z80, com barreiras de memória antes e depois.
