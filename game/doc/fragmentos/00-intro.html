Visão geral do SGDK o kit de desenvolvimento para Sega Mega Drive

O SGDK (Sega Genesis Development Kit), na versão 2.11, é um kit de desenvolvimento gratuito criado por Stéphane Dallongeville que permite programar em linguagem C para o Sega Mega Drive / Genesis, gerando imagens de ROM prontas para rodar em hardware real ou emuladores.

O que é o SGDK

O SGDK 2.11 é composto por três grandes blocos:

  • Biblioteca C — a biblioteca de desenvolvimento em si (com todo o código-fonte incluso), cobrindo vídeo (VDP), sprites, som, DMA, matemática de ponto fixo, controles (joypads), memória e muito mais;
  • Toolchain GCC — o SGDK usa o compilador GCC com alvo m68k-elf e a libgcc para gerar a imagem de ROM. Binários prontos (GCC 13.2) acompanham a distribuição para Windows;
  • Ferramentas em Java — utilitários próprios para compilar recursos (assets), sendo o principal deles o rescomp (compilador de recursos). Por isso o Java precisa estar instalado no sistema.

A biblioteca e as ferramentas do SGDK são distribuídas sob a licença MIT. O compilador GCC e a libgcc permanecem sob licença GNU (GPL3), e qualquer software construído com eles (como a própria biblioteca SGDK) fica sob a GCC runtime library exception.

Autor e mantenedor: Stéphane Dallongeville — repositório oficial em https://github.com/Stephane-D/SGDK, com suporte via Patreon e servidor Discord da comunidade.

Arquitetura do Mega Drive em resumo

Para usar bem o SGDK é essencial conhecer, ao menos superficialmente, o hardware alvo:

ComponenteDescrição
CPU principal — Motorola 68000Processador de 16/32 bits rodando a aproximadamente 7,67 MHz (NTSC). É onde roda o seu código C compilado pelo GCC m68k-elf.
CPU secundária — Zilog Z80Processador de 8 bits (~3,58 MHz) dedicado principalmente ao som: os drivers de áudio do SGDK (XGM, XGM2, PCM etc.) rodam nele, liberando o 68000 para a lógica do jogo.
VDP (Video Display Processor)Chip de vídeo com dois planos de fundo roláveis (Plano A e Plano B) mais um plano Window fixo; até 80 sprites de hardware em tela; 64 KB de VRAM para tiles, tilemaps e tabelas de sprites; e CRAM com 64 cores simultâneas organizadas em 4 subpaletas de 16 cores.
Som — YM2612 + PSGSintetizador FM Yamaha YM2612 com 6 canais (um deles utilizável como DAC para samples PCM) e o PSG (SN76489) com 3 canais de onda quadrada + 1 de ruído, herdado do Master System.

Toda a parte gráfica do Mega Drive é baseada em tiles de 8x8 pixels: imagens de fundo são tilemaps que referenciam tiles na VRAM, e sprites são compostos por blocos de tiles. Essa lógica permeia o SGDK inteiro — em especial os recursos gerados pelo rescomp (TILESET, TILEMAP, MAP, IMAGE, SPRITE).

Como a biblioteca se organiza

Na prática, você não precisa conhecer a estrutura interna dos headers: o SGDK fornece um header guarda-chuva chamado genesis.h que inclui todos os módulos da biblioteca (sys, memory, vdp, vdp_bg, vdp_spr, vdp_tile, pal, dma, map, bmp, sprite_eng, sound, joy, maths, string, timer, tools etc.). Basta uma única linha em cada arquivo-fonte:

#include <genesis.h>

A partir daí todas as funções da API (com prefixos como VDP_, SYS_, SPR_, PAL_, XGM_, JOY_...) ficam disponíveis. A documentação de referência completa (Doxygen, gerada a partir dos headers) está publicada em http://stephane-d.github.io/SGDK/.

O SGDK exige familiaridade prévia com a linguagem C. Aprender C ao mesmo tempo em que se aprende a programar o Mega Drive é fortemente desaconselhado pelo próprio autor — o resultado costuma ser frustração dobrada.

Instalação e primeiro build Windows, Linux/macOS, variável GDK e emuladores

Como instalar o SGDK no Windows (onde os binários já vêm prontos) e nas demais plataformas, configurar a variável de ambiente GDK, compilar um projeto com o makefile oficial e testar a ROM resultante em um emulador.

Windows (caminho recomendado)

No Windows a instalação é a mais simples, pois o pacote do SGDK já inclui os binários pré-compilados do GCC 13.2 (alvo m68k-elf) e as ferramentas auxiliares. Os passos essenciais são:

  1. Baixar a release do SGDK no GitHub e extrair em uma pasta sem espaços no caminho (por exemplo C:\sgdk);
  2. Instalar o Java (JRE/JDK), necessário para as ferramentas de recursos como o rescomp;
  3. Definir a variável de ambiente GDK apontando para a pasta de instalação e, opcionalmente, adicionar %GDK%\bin ao PATH.

Linux, macOS e outras plataformas

Fora do Windows os binários do GCC não acompanham o pacote — você precisa providenciar o toolchain m68k-elf por conta própria. As opções mais usadas:

  • Compilar o GCC m68k-elf manualmente (ou instalá-lo via gerenciador de pacotes, quando disponível);
  • Docker — a solução recomendada é a imagem de Doragasu (https://gitlab.com/doragasu/docker-sgdk), que usa compilador Linux nativo (rápida e simples);
  • Wrappers/ambientes prontos — o MarsDev de Andy Grind (https://github.com/andwn/marsdev) funciona em todos os sistemas, é compatível com o SGDK e ainda suporta 32X; há também o SGDK_wine (rodar o kit via Wine), o sgdk-helper de tlsa (ambiente nativo ou em contêiner) e o gendev-macos para macOS;
  • VS Code — a extensão Genesis-Code (zerasul) integra build e execução; o SGDK inclui um template de projeto para VS Code em project/template.

A variável GDK e a compilação

Todo o sistema de build gira em torno da variável de ambiente GDK, que aponta para a raiz da instalação do SGDK. Com ela definida, compilar um projeto é executar, na pasta do projeto:

# Windows (usando o make incluso em %GDK%\bin)
%GDK%\bin\make -f %GDK%\makefile.gen

# Linux / macOS (toolchain nativo)
make -f $GDK/makefile.gen

O makefile oficial (makefile.gen) cuida de tudo: compila os fontes C/assembly de src/, invoca o rescomp para os arquivos .res de res/, faz o link e gera a ROM final em:

out/rom.bin

Esse arquivo rom.bin é a imagem de ROM pronta para ser carregada em um emulador ou gravada em um flashcart (Everdrive, Mega Everdrive etc.) para rodar no console real.

Emuladores recomendados e documentação

  • BlastEm — o emulador mais preciso disponível, ideal para validar o comportamento próximo do hardware real (inclui debugger);
  • Gens KMod — versão modificada do Gens com ferramentas de depuração voltadas ao desenvolvimento (visualização de VRAM, planos, sprites, mensagens de debug do SGDK).

Sempre teste em mais de um emulador — e, se possível, em hardware real — antes de publicar: emuladores menos precisos podem mascarar bugs de timing e de acesso ao VDP.

A referência oficial de instalação e os tutoriais de primeiros passos estão no wiki oficial: https://github.com/Stephane-D/SGDK/wiki. A documentação de API (Doxygen) fica em http://stephane-d.github.io/SGDK/, e a comunidade se concentra no Discord do SGDK e no fórum Spritesmind.

Estrutura de um projeto SGDK pastas, ciclo de build e o "Hello world"

Todo projeto SGDK segue uma convenção simples de diretórios que o makefile oficial reconhece automaticamente: fontes em src/, recursos em res/, headers em inc/ e a ROM final em out/.

Layout de diretórios

PastaConteúdo
src/Código-fonte C (.c) e assembly (.s) do jogo. O ponto de entrada é a função main(). Um rom_header.c opcional permite personalizar o cabeçalho da ROM (nome do jogo, região, suporte a SRAM etc.).
res/Recursos (assets): imagens PNG/BMP, músicas VGM/XGM, sons WAV, mapas TMX... acompanhados dos arquivos de declaração .res que o rescomp compila.
inc/Headers (.h) do próprio projeto. Os headers gerados pelo rescomp a partir dos .res também ficam acessíveis para inclusão.
out/Saída do build: objetos intermediários, listagens, símbolos e a ROM final out/rom.bin.

Ciclo de build

  1. O rescomp converte cada arquivo .res de res/ em um fonte assembly (.s) contendo os dados binários dos recursos, e gera um header .h com as declarações extern correspondentes;
  2. O GCC m68k-elf compila os fontes de src/ e os assemblies gerados;
  3. O linker junta tudo com a biblioteca do SGDK e a libgcc;
  4. A imagem final é convertida em out/rom.bin, pronta para o emulador ou hardware real.
res/*.res ──rescomp──> out/res/*.s + *.h ─┐
src/*.c  ───gcc (m68k-elf)──> *.o ────────┼──link──> out/rom.out ──objcopy──> out/rom.bin
libmd.a (SGDK) + libgcc ──────────────────┘

Exemplo mínimo real: Hello world

Este é o conteúdo real de sample/basics/hello-world/src/main.c distribuído com o SGDK:

#include <genesis.h>


int main(bool hardReset)
{
    VDP_drawText("Hello world !", 12, 12);

    while(TRUE)
    {
        // nothing to do here
        // ...

        // always call this method at the end of the frame
        SYS_doVBlankProcess();
    }

    return 0;
}

Três pontos merecem destaque:

  • #include <genesis.h> — único include necessário: traz toda a API do SGDK;
  • VDP_drawText("Hello world !", 12, 12) — desenha texto no plano de fundo usando a fonte padrão da biblioteca, na coluna 12 e linha 12 (coordenadas em tiles de 8x8 pixels);
  • SYS_doVBlankProcess() — deve ser chamada ao final de cada frame, dentro do loop principal. Ela sincroniza o jogo com o VBlank (retraço vertical), processa as transferências DMA pendentes, atualiza a leitura dos joypads e executa as tarefas internas da biblioteca. É o "coração" do loop de jogo no SGDK.

Repare que main() recebe um parâmetro bool hardReset: o SGDK informa se a inicialização veio de um reset "frio" (ligar o console) ou "quente" (botão RESET), permitindo tratar os dois casos de forma diferente se necessário.

Sistema de recursos: rescomp compilando assets em dados prontos para a ROM

O rescomp é o compilador de recursos do SGDK (ferramenta Java): ele lê arquivos de declaração .res, converte imagens, músicas e dados binários para os formatos internos da biblioteca e gera um fonte assembly (formato GAS) mais um header .h com as declarações para uso no código C.

O que é o rescomp e como funciona

O SGDK depende fortemente de recursos compilados: em vez de converter imagens e sons manualmente, você escreve um arquivo texto .res em que cada linha declara um recurso (tipo, nome, arquivo de origem e opções). Uso na linha de comando (o makefile oficial já faz isso por você):

rescomp input [output] [-noheader] [-dep <target_file>]

    input      arquivo de recursos de entrada (.res)
    output     nome do arquivo assembly de saída (se omitido, usa o nome do input com extensão .s)
    -noheader  não gerar o arquivo header (.h)
    -dep       gerar arquivo de dependências (.d) para o make (experimental)

Exemplo de arquivo .res real (do sample basics/image):

IMAGE logo_aplib "sgdk.png" APLIB
IMAGE logo_ucomp "sgdk.png" NONE

Para cada .res o rescomp gera um header homônimo (ex.: gfx.res → gfx.h) com declarações extern dos recursos. No código basta incluir o header e usar as variáveis:

// gfx.h (gerado automaticamente pelo rescomp)
extern const Image logo_aplib;
extern const Image logo_ucomp;

// main.c
#include <genesis.h>
#include "gfx.h"

VDP_drawImage(BG_A, &logo_ucomp, 0, 0);

Tipos de recurso suportados

TipoUso
PALETTEPaleta de cores (entrada para Bitmap, Image e Sprite)
BITMAPImagem bitmap para o engine BMP do SGDK (não usar como recurso de tiles)
TILESETConjunto de tiles compartilhável entre TILEMAP e MAP
TILEMAPTilemap "cru" para desenhar imagens/fundos pequenos
MAPMapa otimizado para fundos/fases grandes
OBJECTSArray de objetos customizados de mapas Tiled (TMX)
IMAGEImagem completa (Palette + TileSet + TileMap) para planos de fundo
SPRITEDefinição de sprite para o Sprite engine do SGDK
XGM / XGM2Música (VGM/XGM) para os drivers XGM e XGM2
WAVSample de som PCM para os drivers de áudio
BINDados binários arbitrários, sem conversão específica
ALIGN / UNGROUP / NEARFunções auxiliares que controlam alinhamento, agrupamento e posicionamento (FAR/NEAR) dos dados no arquivo

Nota importante sobre formatos de imagem

Vários tipos de recurso usam imagens (BMP ou PNG) como entrada, e o rescomp aceita imagens RGB e imagens de cor indexada:

  • Imagens RGB — como não há informação de paleta, ela deve estar desenhada no canto superior esquerdo da imagem: cada cor em um tile de 8x8 e cada subpaleta (16 cores) em uma linha de tiles separada. É preciso incluir as 4 subpaletas (4x16 cores) mesmo que só a primeira seja usada. O rescomp remove automaticamente essa área da imagem durante o processamento (veja rgb_example.png em sample/game/sonic/res/gfx);
  • Imagens indexadas — suporte a 8bpp, 4bpp, 2bpp e 1bpp; a paleta é lida diretamente da imagem (a cor de índice 0 é a cor transparente). Com imagens 8bpp, os índices de cor ≥ 128 podem carregar informação extra por tile: bits 4-5 = índice da paleta (0-3), bit 7 = prioridade (0=LOW, 1=HIGH); o bit 6 é ignorado. Todos os pixels de um mesmo tile 8x8 devem usar o mesmo valor extra, senão o rescomp gera erro.

O rescomp também suporta extensões: é possível criar tipos de recurso próprios em Java, exportar como [nome]_ext.jar e colocar o jar na mesma pasta dos arquivos .res — ele é detectado automaticamente.

PALETTE

Converte um arquivo .pal (Paint Shop Pro) ou uma imagem em uma estrutura Palette do SGDK. Usada como fonte de cores para recursos Bitmap, Image e Sprite.

PALETTE name file
ParâmetroDescrição
nameNome da estrutura de saída
fileCaminho da imagem de entrada (BMP ou PNG) ou arquivo PAL (paleta Paint Shop Pro). Vale a nota sobre formatos de imagem acima.

Exemplo real (sample Sonic):

PALETTE palette_all "gfx/S1_GHZ1_FG.png"

Header gerado: extern const Palette palette_all; — carregue com PAL_setPalette(PAL0, palette_all.data, DMA);

BITMAP

Converte uma imagem em uma estrutura Bitmap do SGDK, destinada ao engine BMP (framebuffer por software). Não deve ser usada para imagens baseadas em tiles.

BITMAP name img_file [compression]
ParâmetroDescrição
nameNome da estrutura Bitmap de saída
img_fileCaminho da imagem de entrada (BMP ou PNG)
compressionCompressão (descompacte com unpackBitmap(..)): -1/BEST/AUTO = melhor compressão; 0/NONE = sem compressão (padrão); 1/APLIB = aplib (ótima taxa, lenta); 2/FAST/LZ4W = LZ4 customizado (taxa média, rápido)

Exemplo:

BITMAP logo_bmp "gfx/logo.png" BEST

Header gerado: extern const Bitmap logo_bmp;

TILESET

Converte uma imagem ou arquivo TSX (Tiled) em uma estrutura TileSet, usada como fonte de tiles para recursos Image, Tilemap, Map e Sprite. Se a entrada já for um tileset "de verdade" (como uma fonte de caracteres), use opt = NONE para não remover tiles duplicados.

TILESET name file [compression [opt [ordering [export]]]]
ParâmetroDescrição
nameNome da estrutura TileSet de saída
fileCaminho do arquivo de entrada (BMP, PNG ou TSX do Tiled)
compressionCompressão (descompacte com unpackTileSet(..)): -1/BEST/AUTO, 0/NONE (padrão), 1/APLIB, 2/FAST/LZ4W
optNível de otimização: 0/NONE = nenhuma (cada tile é único); 1/ALL = ignora tiles duplicados e espelhados (padrão); 2/DUPLICATE = ignora apenas duplicados
orderingOrdem de processamento dos tiles: ROW = por linha (padrão); COLUMN = por coluna
exportExportação do tileset otimizado em PNG: 0/FALSE = não exporta (padrão); 1/TRUE = exporta como <file>-tileset-export.png

Exemplo real (sample Sonic):

TILESET bga_tileset "gfx/S1_GHZ1_FG.png" BEST ALL

Header gerado: extern const TileSet bga_tileset;

Com imagem 8bpp indexada é possível embutir, nos bits extras da cor, o índice de paleta (bits 4-5) e a prioridade (bit 7) por tile — desde que todos os pixels do tile 8x8 usem o mesmo valor.

TILEMAP

Converte uma imagem ou um arquivo TMX (Tiled) em uma estrutura TileMap, usada para desenhar em um plano de fundo. Requer um tileset, que pode ser compartilhado entre vários tilemaps. Não é indicado para fases grandes (ocupa muito espaço) — para isso use o recurso MAP.

Sintaxe com imagem como entrada:

TILEMAP name img_file tileset_id [compression [map_opt [map_base [ordering]]]]
ParâmetroDescrição
nameNome da estrutura TileMap de saída
img_fileCaminho da imagem de entrada (BMP ou PNG)
tileset_idRecurso TILESET base a usar (permite compartilhar o tileset entre vários tilemaps)
compressionCompressão (descompacte com unpackTileMap(..)): -1/BEST/AUTO, 0/NONE (padrão), 1/APLIB, 2/FAST/LZ4W
map_optOtimização do tilemap: 0/NONE = nenhuma; 1/ALL = detecta tiles duplicados e espelhados (padrão); 2/DUPLICATE = apenas duplicados
map_baseValor base do tilemap: define prioridade, paleta e deslocamento de índice de tile padrão. Usar um offset de índice fixo (alocação estática de tiles) permite empregar as funções mais rápidas VDP_setTileMapxxx(..)
orderingOrdem de processamento: ROW (padrão) ou COLUMN

Sintaxe com arquivo TMX (Tiled, dados de mapa em CSV) como entrada:

TILEMAP name tmx_file layer_id [ts_compression [map_compression [map_base]]]
ParâmetroDescrição
nameNome da estrutura TileMap de saída
tmx_fileCaminho do arquivo TMX (com dados de mapa codificados em CSV)
layer_idNome da camada (layer) da qual extrair os dados do mapa
ts_compressionCompressão do tileset: -1/BEST/AUTO, 0/NONE (padrão), 1/APLIB, 2/FAST/LZ4W
map_compressionCompressão do mapa (mesmos valores de ts_compression)
map_baseValor base do tilemap (prioridade, paleta e offset de índice de tile padrão)

Exemplo:

TILESET fundo_ts  "gfx/fundo.png" FAST
TILEMAP fundo_tm  "gfx/fundo.png" fundo_ts FAST ALL 0

Header gerado: extern const TileMap fundo_tm;

Com TMX é possível definir a prioridade de duas formas: (1) duas camadas com sufixos ' low' e ' high' no nome; ou (2) uma camada principal mais uma camada com sufixo ' priority'/' prio' contendo a informação 0/1 — nesse caso um tile 8x8 totalmente transparente vale prioridade LOW e um tile com ao menos 1 pixel opaco vale HIGH.

MAP

Converte uma imagem ou arquivo TMX em uma estrutura Map, otimizada para fundos/fases grandes: usa uma codificação avançada (blocos comprimidos) que ocupa muito menos ROM que um recurso IMAGE equivalente. É o recurso indicado para níveis de jogo com scroll.

Sintaxe com imagem:

MAP name img_file tileset_id [compression [map_base]]
ParâmetroDescrição
nameNome da estrutura Map de saída
img_fileCaminho da imagem de entrada (BMP ou PNG)
tileset_idRecurso TILESET base (compartilhável entre vários mapas)
compressionCompressão: -1/BEST/AUTO, 0/NONE (padrão), 1/APLIB, 2/FAST/LZ4W
map_baseValor base do tilemap (prioridade, paleta e offset de índice de tile padrão); com alocação estática de tiles a decodificação interna do MAP fica mais rápida

Sintaxe com TMX:

MAP name tmx_file layer_id [ts_compression [map_compression [map_base [ordering]]]]
ParâmetroDescrição
nameNome da estrutura Map de saída
tmx_fileCaminho do arquivo TMX (dados de mapa em CSV)
layer_idNome da camada da qual extrair os dados
ts_compressionCompressão do tileset: -1/BEST/AUTO, 0/NONE (padrão), 1/APLIB, 2/FAST/LZ4W
map_compressionCompressão do mapa (mesmos valores)
map_baseValor base do tilemap (prioridade, paleta, offset de índice)
orderingOrdem de processamento: ROW (padrão) ou COLUMN

Exemplo real (sample Sonic — dois planos com tilesets próprios):

TILESET bga_tileset "gfx/S1_GHZ1_FG.png" BEST ALL
TILESET bgb_tileset "gfx/S1_GHZ1_BG.png" BEST ALL

MAP bga_map "gfx/S1_GHZ1_FG.png" bga_tileset BEST 0
MAP bgb_map "gfx/S1_GHZ1_BG.png" bgb_tileset BEST 0

Header gerado: extern const MapDefinition bga_map; — use com MAP_create(&bga_map, BG_A, ...) e MAP_scrollTo(..).

Valem as mesmas dicas do TILEMAP: bits extras em imagens 8bpp (paleta nos bits 4-5, prioridade no bit 7) e camadas TMX com sufixos ' low'/' high' ou camada ' priority' para definir prioridade.

OBJECTS

Converte um arquivo TMX (Tiled) em um array de ponteiros para objetos customizados — útil para definir entidades, eventos, gatilhos e qualquer coisa que você queira "anexar" a um MAP. Os objetos vêm das object layers do Tiled; desde o Tiled 1.8 é possível definir tipos de objeto próprios. Objetos baseados em arquivos de template (.tx) não são suportados (são ignorados).

OBJECTS name tmx_file layer_id field_defs [sortby:<field>] [decl_type [type_filter]]
ParâmetroDescrição
nameNome do array de objetos de saída
tmx_fileCaminho do arquivo TMX
layer_idNome do grupo/camada de objetos a exportar
field_defsCampos a exportar (e a ordem de extração) no formato <nome>:<tipo> separados por ;. Tipos aceitos: u8, s8, u16, s16, u32, s32, f16, f32, bool, string, object. Ex.: "type:u16;name:string;x:f32;y:f32;tileindex:u32". Campos não encontrados são simplesmente ignorados.
sortbyCampo usado para ordenar os objetos, ex.: sortby:x. Sem ele, a ordenação usa (nesta ordem) os campos index, ind, tileIndex, id.
decl_typeTipo de declaração dos objetos (padrão void); pode ser um tipo próprio como "Entity"
type_filterFiltro por tipo: extrai apenas objetos Tiled do tipo indicado

Correspondência de tipos Tiled → SGDK: bool→bool; color→u32; float→f32,f16,s32,u32,s16,u16; int→f32,f16,s32,u32,s16,u16,s8,u8; Object→object (internamente void*); string→string (internamente char*); Enum→u8,u16,u32 (salve como número, não string); file e list não são suportados.

Exemplo:

OBJECTS level1_entities "maps/level1.tmx" "entities" "type:u16;x:f32;y:f32" sortby:x Entity

Atributos padrão do Tiled (id, name, visible, x/y, width/height, text) só são exportados se você adicionar no objeto um campo booleano habilitador com valor true: exportId, exportName, exportVisible, exportPosition, exportSize, exportText. Há ainda exportTileIndex, que exporta o índice do tile (x + y * map_width) no campo tileIndex e ordena os objetos por ele, viabilizando buscas rápidas por posição.

IMAGE

Converte uma imagem em uma estrutura Image do SGDK, que embute internamente Palette, TileSet e TileMap. É a forma mais direta de desenhar uma imagem completa em um plano de fundo. Para fases grandes, prefira MAP (IMAGE consome muito espaço em ROM).

IMAGE name img_file [compression [map_opt [map_base]]]
ParâmetroDescrição
nameNome da estrutura Image de saída
img_fileCaminho da imagem de entrada (BMP ou PNG)
compressionCompressão (descompacte com unpackImage(..)): -1/BEST/AUTO, 0/NONE (padrão), 1/APLIB, 2/FAST/LZ4W
map_optOtimização do tilemap: 0/NONE, 1/ALL (padrão, detecta duplicados e espelhados), 2/DUPLICATE
map_baseValor base do tilemap (prioridade, paleta e offset de índice de tile). Com offset estático é possível usar as funções mais rápidas VDP_xxxTileMapxxx(..)

Exemplo real (sample basics/image — a mesma imagem com e sem compressão):

IMAGE logo_aplib "sgdk.png" APLIB
IMAGE logo_ucomp "sgdk.png" NONE

Header gerado: extern const Image logo_aplib; — desenhe com VDP_drawImage(BG_A, &logo_ucomp, x, y);

SPRITE

Converte uma folha de sprites (spritesheet) em uma estrutura SpriteDefinition para o Sprite engine do SGDK. Internamente contém várias estruturas TileSet, Palette e Animation. A imagem de entrada é uma grade: cada célula é um frame e cada linha é uma animação completa.

SPRITE name img_file width height [compression [time [collision [opt_type [opt_level [opt_duplicate]]]]]]
ParâmetroDescrição
nameNome da estrutura SpriteDefinition de saída
img_fileCaminho da imagem de entrada (BMP ou PNG)
widthLargura de um frame: em tiles (deve ser < 32), em pixels com sufixo p (múltiplo de 8, ex.: 32p) ou em número de frames na largura com sufixo f (ex.: 4f)
heightAltura de um frame: mesmas convenções de width (ex.: 16p, 1f)
compressionCompressão: -1/BEST/AUTO, 0/NONE (padrão), 1/APLIB (boa taxa, lenta — evite em sprites com streaming), 2/FAST/LZ4W (recomendada para sprites com streaming)
timeDuração de cada frame em 1/60 s. 0 (padrão) desativa a animação automática. Pode ser global (um valor) ou por frame/animação, ex. para 3 animações x 5 frames: [[3,3,3,4,4][4,5,5][2,3,3,4]] (sem espaços; valores vazios permitidos para frames vazios)
collisionTipo de colisão: CIRCLE, BOX ou NONE (padrão). Por padrão os limites de colisão usam 75% do frame original
opt_typeEstratégia de corte em sprites de hardware: 0/BALANCED = equilíbrio entre tiles e sprites de hardware (padrão); 1/SPRITE = menos sprites de hardware (sprites maiores, mais tiles); 2/TILE = menos tiles (mais sprites de hardware menores); 3/NONE = sem otimização (cobre o frame inteiro)
opt_levelNível de otimização do corte: 0/FAST = rápido, bom em geral (padrão); 1/MEDIUM = melhor que FAST, ~10x mais lento; 2/SLOW = algoritmo genético (80.000 iterações), ~25x mais lento; 3/MAX = algoritmo genético (500.000 iterações), ~150x mais lento
opt_duplicateRemoção de frames consecutivos duplicados: FALSE (padrão) = não remove (os dados de pixel duplicados ainda são otimizados pelo otimizador binário); TRUE = mantém só a primeira ocorrência e aumenta o timer para compensar — atenção: isso altera animation.numFrame

Como a SpriteDefinition é gerada:

  • As dimensões da imagem devem ser múltiplas de 8 (alinhadas em tile); cada célula da grade é um frame e cada linha uma animação (máximo de 255 frames por animação);
  • O tamanho do frame (width x height em tiles) deve ficar abaixo de 32 tiles por eixo (máximo de 248 pixels);
  • Um frame pode ser composto por vários sprites de hardware do VDP, limitado a 16 sprites de hardware por frame — se não couber, o rescomp reclama e você deve reduzir ou dividir o sprite;
  • O rescomp detecta frames espelhados (evitando tiles redundantes), frames vazios ao final da linha (não armazenados), frames copiados dentro da animação (gera a sequência correspondente) e áreas vazias dentro dos frames (economizando sprites de hardware e VRAM).

Exemplos reais (sample Sonic):

SPRITE sonic_sprite   "sprite/sonic.png"   6 6 FAST 5
SPRITE enemy01_sprite "sprite/enemy01.png" 6 4 BEST 5
SPRITE sbar_sprite    "sprite/sbar.png"    1 3 FAST 0

Header gerado: extern const SpriteDefinition sonic_sprite; — instancie com SPR_addSprite(&sonic_sprite, x, y, TILE_ATTR(PAL0, ...));

Quando opt_level é informado (valor não vazio), o rescomp salva automaticamente uma imagem <imagem>_opt.png mostrando o resultado do corte em sprites de hardware — ótimo para depurar o consumo de VRAM.

XGM

Converte um arquivo de música VGM ou XGM em formato binário utilizável com XGM_startPlay(..). O driver XGM toca música com mixagem de 4 canais PCM, rodando 100% na CPU Z80.

XGM name file [timing [options]]
ParâmetroDescrição
nameNome da variável da música XGM
fileCaminho do arquivo .vgm ou .xgm a converter
timingBase de tempo do XGM: -1 (padrão) = AUTO (NTSC ou PAL conforme o arquivo de origem); 0 = NTSC; 1 = PAL
optionsParâmetros opcionais repassados ao xgmtool, ex.: "-dr -di" para desativar processamentos automáticos de samples

Exemplo:

XGM musica_fase1 "music/fase1.vgm" -1

Header gerado: extern const u8 musica_fase1[];

XGM2

Converte um ou mais arquivos VGM para o formato do driver XGM2, utilizável com XGM2_play(..) ou XGM2_playTrack(..). O XGM2 mixa 3 canais PCM (100% no Z80) com volume ajustável (FM e PSG).

Sintaxe para faixa única:

XGM2 name file [options]

Sintaxe multi-faixas (permite compartilhamento de PCM entre as faixas):

XGM2 name file1 [file2] [...] [options]
ParâmetroDescrição
nameNome da variável da música XGM2
file(s)Caminho(s) do(s) arquivo(s) .vgm. Aceita vários arquivos ou curinga, ex.: "music1.vgm" "music2.vgm" ou "*.vgm"
optionsParâmetros opcionais para o xgm2tool; devem sempre começar com - (ex.: "-dr -di"), caso contrário não são reconhecidos

Exemplo real (sample Sonic):

XGM2 sonic_music "music/sonic1.vgm"

Header gerado: extern const u8 sonic_music[];

WAV

Converte um arquivo .wav em formato binário utilizável com um dos drivers PCM do SGDK. O rescomp converte automaticamente o áudio para o formato exigido pelo driver escolhido.

WAV name wav_file driver [out_rate [far]]
ParâmetroDescrição
nameNome da variável do sample
wav_fileCaminho do arquivo .wav (convertido automaticamente para o formato correto)
driverDriver Z80 alvo:
PCM/DEFAULT — 1 canal PCM, sample 8 bits com sinal, de 8 a 32 kHz; use SND_PCM_startPlay(..).
DPCM2 — 2 canais DPCM (4 bits) a 22050 Hz fixos; use SND_DPCM2_startPlay(..).
PCM4 — 4 canais PCM (8 bits com sinal) a 16 kHz fixos com 16 níveis de volume; use SND_PCM4_startPlay(..).
XGM — mixa até 4 samples (8 bits) a 14 kHz junto com a música XGM; use XGM_setPCM(..) e XGM_startPlayPCM(..).
XGM2 — mixa até 3 samples (8 bits) a 13,3 ou 6,65 kHz junto com a música XGM2; use XGM2_playPCM(..).
(Os antigos valores numéricos 0-5 e o nome 2ADPCM não são mais aceitos.)
out_rateTaxa de saída do PCM — relevante apenas para os drivers PCM e XGM2. PCM aceita: 8000, 11025, 13400, 16000, 22050, 32000 (padrão 16000). XGM2 aceita apenas 6650 ou 13300 (padrão 13300)
farFlag de dado binário "far" — coloca o dado no final da ROM (útil para bank switch). Padrão: TRUE

Exemplos reais (sample Sonic):

WAV sonic_jump_sfx "sfx/S1_jump.wav" XGM2 6650
WAV sonic_roll_sfx "sfx/S1_roll.wav" XGM2

Header gerado: extern const u8 sonic_jump_sfx[];

BIN

Incorpora qualquer arquivo de dados na ROM como um array binário acessível pelo código, sem conversão ou processamento específico — ideal para tabelas pré-calculadas, dados de fase próprios, fontes binárias etc.

BIN name file [align [size_align [fill [compression [far]]]]]
ParâmetroDescrição
nameNome da variável do array de dados
fileCaminho do arquivo de dados a converter
alignAlinhamento do endereço de memória do array gerado (padrão: 2)
size_alignAlinhamento do tamanho do array gerado (padrão: 2)
fillValor de preenchimento usado para completar o alinhamento de tamanho (padrão: 0)
compressionCompressão: 0/NONE, 1/APLIB (boa taxa, lenta), 2/FAST/LZ4W (taxa média, rápida)
farFlag "far" — posiciona o dado no final da ROM (útil para bank switch). Padrão: TRUE

Exemplo:

BIN nivel1_dados "data/nivel1.dat" 2 2 0 LZ4W

Header gerado: extern const u8 nivel1_dados[];

ALIGN

Função (diretiva) que alinha os dados binários do arquivo de recursos inteiro — portanto só pode haver uma diretiva ALIGN por arquivo .res. É útil com bank switch em ROMs maiores que 4 MB, para evitar que um bloco de dados cruze dois bancos. Se precisar de alinhamentos diferentes, use vários arquivos .res.

ALIGN [value]
ParâmetroDescrição
valueAlinhamento mínimo dos dados binários, em bytes. Se omitido, o padrão é 524288 (512 KB), que é o tamanho do banco no mecanismo de bank switch

Exemplo:

ALIGN
BIN fase_grande "data/fase_grande.dat"

UNGROUP

Por padrão o rescomp agrupa a exportação dos dados por tipo, o que geralmente melhora a compressão LZ4W. A função UNGROUP desativa esse agrupamento — útil para ajudar na separação de dados por banco quando se usa o mecanismo de bank switch.

UNGROUP

Sem parâmetros; vale para todo o arquivo .res em que aparece.

NEAR

Por padrão, todos os dados binários são exportados como "FAR": ficam no final da ROM e podem exigir o mecanismo de bank switch se a ROM passar de 4 MB. A função NEAR força todos os dados binários do arquivo .res a serem posicionados antes dos dados FAR na ROM — garantindo acesso direto sem troca de banco.

NEAR

Sem parâmetros; vale para todo o arquivo .res em que aparece.

Regra prática para ROMs grandes: dados acessados o tempo todo (código de fase, tabelas quentes) devem ser NEAR; assets volumosos e de acesso pontual (músicas, imagens de telas) podem permanecer FAR, combinados com ALIGN/UNGROUP para organizar os bancos.
